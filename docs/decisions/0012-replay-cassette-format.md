# 0012 · 回放录音带：接缝在哪、文件长什么样

> ⚠ **这份是草案。** 阶段 3 定格式和机制，**阶段 4 才录第一盘**。
> 定在录之前是有意的：录音带是数据，数据一旦有存量，改格式的成本就翻倍。

## 背景

三层测试策略（`ts-modern-train/docs/engineering/25`）的第二层。
契约测试（第一层）证明的是「每个实现都守我写下的约」；
**回放证明的是「我写下的约和真实世界对得上」** —— 前者拦不住「我对 provider 的理解错了」。

现在录 0 盘，阶段 4 会录几十盘。和 `engineering/24 数据形状` 同一个机理：
**过了第一次有存量的那一刻，代码成本不变，数据成本变成无穷。**

## 候选与决定

### ① 接缝（seam）定在哪

**seam**：能在不改被测代码的前提下换掉一段行为的地方。

```text
  用例层 ─► LlmPort ─► 适配器 ─► HTTP 客户端 ─► 网络 ─► 真模型
              ↑           ↑           ↑
            seam①      seam②      seam③

候选   ①  在 LlmPort 上放一个 ReplayLlm
       ②  ★在 HTTP 响应体上★：适配器收一个 fetch 形状的函数
       ③  在网络字节上：拦 undici / MockAgent

判据   ★可执行★：把真适配器装上，跑一遍回放测试，看★适配器文件的覆盖率★
       ①  ReplayLlm 自己就是 LlmPort 实现，它★顶替掉★真适配器
          ⇒ 适配器覆盖率是 ★0★，不是「低」。而适配器正是回放要测的东西
       ②  覆盖解析 + 错误映射 + 用例层
       ③  ②再加 HTTP 客户端，但★绑死在 HTTP 库的实现细节上★，换库全废

选择   ②
代价   测不到 HTTP 客户端本身（连接池、重定向、keep-alive、代理）。
       ⚠ ★反悔信号★：出现一个「回放全绿但真调挂」且原因在传输层的 bug，
         那时才考虑加一层 ③，而不是现在就上
```

### ② 接缝具体长什么样

```text
候选   a  猴补丁 globalThis.fetch
       b  ★适配器构造函数收一个 fetch 形状的函数★
       c  自定义 HttpClient 接口（自己定 request/response 类型）

判据   ★「同一个进程里能不能同时跑两个用不同录音带的测试」★
       a 不行 —— 全局单例，vitest 并发跑文件时互相踩
       c 能，但要自己维护一套和 Response 平行的类型，
         ★两份平行结构会各自漂移★（loop.ts / turn.ts 已经踩过，见 0002）

选择   b   type FetchLike = (input, init) => Promise<Response>
代价   适配器多一个构造参数（默认值是全局 fetch，所以生产代码不受影响）
       ⚠ 前提：SDK 要接受注入的 fetch。★阶段 4 第一件事就是验这一条★ ——
         验不过的话本条要重定，退路是 c
```

### ③ 匹配键：回放时靠什么找到对应那一盘

```text
候选   a  调用顺序（第 1 次请求配第 1 盘）
       b  请求内容的哈希
       c  ★显式 name★

判据   ①「测试里插一行请求，会不会让后面全部错位」—— a 会
       ②「打开文件能不能看出这是哪一盘」—— b 看不出（文件名是一串十六进制）
       ③「录制和回放不匹配时，报错够不够定位」—— c 直接报名字

选择   c
代价   每盘要起名字（多写一个字符串）。
       ⚠ 同名覆盖是静默的 ⇒ ★录制器要在写盘前检查重名并拒绝★，
         这条不做的话「重录一盘」会悄悄改掉另一个测试的输入
```

### ④ 存不存请求

```text
候选   a  只存响应
       b  ★存请求 + 响应★

判据   「★我发出去的形状对不对★ 能不能被验」——
       a 验不了。而那正是 provider 400 的主要来源
       （DeepSeek 兼容端点已知：messages[] 里塞 role:"system" 直接 400）

选择   b，请求体存全量
代价   录音带变大；★system prompt 和用户输入进了 Git★
       ⚠ ★反悔信号★：语料换成真实用户数据的那天，本条必须改
         （现在的语料是本仓库自己的 docs/，是我们自己的东西）
```

### ⑤ 录制模式怎么触发

```text
候选   a  环境变量 RECORD=1
       b  ★单独的 pnpm record 脚本★
       c  缺带子时自动录

判据   ★「CI 上会不会意外真调模型」★ ——
       c 会：CI 上缺一盘带子就去打真 API，★花钱、变慢、还不确定★
       a 会：环境变量泄进 CI 是常见事故

选择   b。★缺带子 = 测试红，不是自动补录★
代价   加一个新场景要手动跑一次录制
```

### ⑥ 文件名与元信息

```text
选择   cassettes/<provider>-<scenario>-<yyyy-mm-dd>-<api-version>.json
判据   engineering/25「★录完就开始腐烂★」—— ★日期写进文件名★，
       一眼看出这盘多旧，不用打开文件
配套   阶段 4 的 provider 能力矩阵跑同一组契约测试，★那就是重录的时机★；
       重录之后 diff 出来的东西就是 provider 的变更日志
```

### ⑦ 一盘带子里有多次往返时，靠什么配对

> **本节是实现时补的，0012 原稿没有。按 ADR 的规矩这属于「补记」：
> 前六节一句没改，本节只是把当时没想到的一格写下来。**

```text
背景   ③ 定的是「靠什么找到★哪一盘★」。但一盘带子里可能有多次往返
       （重试、多轮工具调用），那一层的配对当时没定

候选   a  ★顺序取★，不核对
       b  ★顺序取 + 每次核对请求指纹★
       c  在带子里也按 name 索引每一次往返

判据   ③ 已经判过「顺序很脆」。但一盘带子内部的顺序是★确定的★
       （同一个场景、同一段代码），脆的是「跨盘插一个请求」那种情况。
       真正的风险变成了另一个：★带子和代码脱节而没人发现★
       —— 换了 system prompt 之后，录的响应已经不是对这个请求的回答了

选择   b。指纹 = method + url + body
代价   ★改 prompt 就要重录★。
       这个代价是★要的★不是忍的：录的响应本来就是对旧 prompt 的回答，
       继续用它就是 engineering/25 说的「回放腐烂」的静默版本
       c 的代价更大：一盘带子内部再起一套名字，录制脚本要人工标注
```

> **2026-09 复核：这个代价是人确认过的，不是我一个人判的。**
> 当时提出的退路是「url + method 必配，body 只警告不拦」，
> 用来换「改一个字的 prompt 不必重录几十盘」。**没有采纳** ——
> 只警告的那一版等于把「带子和代码脱节」变回一条没人读的日志，
> 而那正是 ⑦ 存在的全部理由。body 留在指纹里。

### ⑧ 失败是 reject 还是同步 throw

```text
选择   ★rejected promise★
判据   ★真 fetch 不会同步抛★。同步抛的替身会让调用方的 `.catch()` 漏掉错误 ——
       那正是「Fake 和真货行为不同」的典型形态，也正是契约测试要防的东西
实测   第一版写的是 throw，自己的测试当场红了 4 条（`rejects.toThrow` 收不到）
```

### ⑨ body 只认字符串

```text
选择   ★非字符串 body 当场抛★，不静默变 null
判据   静默变 null 的话，两个内容不同的请求会算出★同一个指纹★ ——
       ⑦ 那道安全带就悄悄失效了。宁可现在炸，不要以后配错
代价   Uint8Array / FormData / 流都不支持。
       ⚠ 和 ② 的 SDK 前提一起，★阶段 4 第一批要验的东西★
另外   校验放在打网络★之前★ —— 反过来的话会花掉一次真调用才发现录不下来，
       而录制正是要花钱的那一步
```

## SAFETY

**录音带是要进 Git 的文件。写进去的秘密等于已经泄露** ——
删 commit 没用，必须去 provider 后台吊销。

```text
① ★白名单，不是黑名单★
   只有明确列出的 header 才写盘。黑名单会漏 ——
   provider 明天加一个新的鉴权头，黑名单不会自己长出来
   写盘的 header：content-type / request-id / retry-after / anthropic-version
② ★抹在写盘前，不是读盘时★
   读盘时抹意味着明文在磁盘上存在过
③ 请求体不做脱敏，理由见 ④ 的反悔信号 —— ★那条一旦触发，本节要一起改★
④ gitleaks 阶段 5 才进栈。在那之前，★录制器自己就是唯一的门禁★
   ⇒ 录制器必须有一个「见红」测试：喂一个带假 key 的响应，确认写出来的文件里没有它
```

## 后果

```text
✅ 回放跨过适配器，测的是「我对 provider 形状的理解」
✅ 格式在有存量之前定死，阶段 4 录的东西不会作废
⛔ 阶段 3 只能建机制和格式，★没有真录制就没有真信号★ ——
   这一层在阶段 4 之前是空的，不要当成已经生效
⛔ 测不到传输层（① 的代价）
```
