# 0013 · Eval：用例长什么样、判据分几档、阈值什么时候定

> ⚠ **这份是草案。** 阶段 3 建骨架和用例格式，**阈值要等阶段 4 量出 `p0` 才能填**。

## 背景

三层里唯一 oracle 不是「等于」的那一层。
`ts-modern-train/docs/engineering/25` 已经把**阈值怎么算**解决了
（二项分布，精确解，`node scripts/bench-eval-threshold.ts` 可复现）。
本文补它没给的另一半：**用例本身长什么样**。

理由和 0012 相同 —— 用例也是数据，也会有存量。攒到 100 条再改格式，
就是 100 条要迁移。而 `engineering/25` 实验 2 的结论正是
**「只有样本量能同时压低假警报和抬高检出力」**，也就是说这份格式注定要长到三位数。

## 候选与决定

### ① 判据分几档，先用哪一档

```text
候选   a  ★程序可判★：结构断言（调了哪个工具 / 几轮内答完 / 答案里有没有某个文件名）
       b  关键词 / 正则
       c  LLM judge（拿另一个模型当裁判）

判据   ★「这条判据自己会不会错」★
       a 不会 —— 它是确定的，错了是我写错了，不是它飘了
       b 会漏（同义改写）不会错判
       c ★会错，而且误差相乘★：概率系统的输出交给另一个概率系统评判
         ⇒ 挂了的时候★分不清挂的是被测对象还是裁判★（engineering/25 坑⑥）

选择   ★a 优先，b 作为过渡，c 暂不引入★
       引入 c 的前置条件（写死在这里，不许绕）：
         ★judge 先和人工标注对齐一次，量出一致率★，一致率进 README
代价   早期能测的性质窄 —— 测得了「调没调 read_file」「三轮内答完了吗」，
       ★测不了「答得好不好」★。
       ⚠ 这不是缺陷：engineering/25 的本质是「大部分根本不用测概率」，
         能被 a 判的部分应该尽量多
```

### ② 用例文件的形状

```text
选择   { id, question, expect: [判据…], tags: [] }
       ★expect 是数组不是单条★

判据   「一条用例能不能同时要求两件事」——
       「docs 下有什么」这条既要求★调了 list_files★，又要求★三轮内答完★。
       拆成两条用例的话，同一个问题会被问两次（★Eval 是按次收费的★）
代价   一条用例失败时要说清是哪一条 expect 挂的 ⇒ 结果里按 expect 逐条记
```

### ③ 结果怎么存

```text
候选   a  只打印，不存
       b  ★每次跑写一个 JSON，进 Git★
       c  存进数据库（阶段 7 才有）

判据   engineering/25：★「Eval 是趋势指标不是门禁」★ —— 趋势需要历史。
       a 没有历史等于没有趋势；c 现在还没有库
选择   b：{ 时间戳, 模型, 通过数/总数, 每条失败用例的 id 和挂的那条 expect }
       ★只存汇总 + 失败明细，不存模型的完整输出★
代价   结果文件会累积。
       ⚠ 不存完整输出 = 事后没法复盘「它当时到底说了什么」
         ⇒ 反悔信号：出现第一次「看数字看不出问题在哪」的时候，改成存输出
         （那时要一起定 redaction —— 和 0012 SAFETY 同一套规矩）
```

### ④ 退出码：现在就写阈值吗

```text
候选   a  低于阈值 k 就非 0（真门禁）
       b  ★永远 0，只报数字★

判据   ★阈值的输入 p0 现在是未知数★（MyAgent 还没接真模型）。
       engineering/25 实验 1 已经量过：n=20 时★决策窗口是空的★ ——
       假警报 <5% 且检出力 >80% 的 k ★一行都没有★
       ⇒ 现在写任何一个 k，都是在「天天误报」和「退化了也不知道」里瞎选一个

选择   b
代价   这一层在阶段 4 之前★不产生任何会红的信号★。
       ⚠ ★这是有意的，不是没做完★ —— 一个永远绿的假门禁比没有门禁更糟，
         因为它会让人以为这件事已经有人管了
⏰ 解除条件（根 README 已有这条待办）：
   ★阶段 4 接上模型的第一件事是量 p0★ —— 同一组用例跑 5–10 轮，
   量出通过率和波动，再回 engineering/25 那张表定 n 和 k
```

### ⑤ 不进 verify

```text
选择   ★pnpm eval 独立，不进 verify★（roadmap 阶段 3 已定，本文只记录理由）
判据   engineering/25 实验 4：单套件通过率 86.7% 时，
       ★10 个套件全绿的概率只有 24.0%★
       ⇒ 概率门禁混进确定门禁，★整条 CI 的语义从「绿=对」塌成「绿=运气不错」★
```

### ⑥ 判分点是闭集，还是自由文本

> **本节起是实现时补的，0013 原稿只有 ①–⑤。按 ADR 的规矩这属于「补记」：
> 前五节一句没改，后三节只是把当时没想到的几格写下来。**

```text
背景   ① 定的是「判据用哪一档」，没定「一条判据长什么样」。
       起草时脑子里默认的是 { kind, ... } 这种形状，但真写的时候
       ★正则/表达式字符串★是更省事的候选，值得写下来为什么没选

候选   a  ★闭集判别联合★：{ kind: "used-tool", tool } 等五格
       b  自由文本 + 正则：{ pattern: "list_files.*README" }
       c  一段小 DSL / 表达式求值

判据   同 ADR 0007 §⑨（ToolOutcome.failed 的 cause 是闭集）：
       ★自由文本挡不住拼错★ —— `{ kind: "user-tool" }` 在 b 和 c 下都是合法输入，
       只会安静地永远不匹配，然后那道题永远挂，而人以为是模型的问题
       另一条：闭集能★枚举「我们现在能判什么」★，自由文本不能

选择   a
代价   加一种判法要改代码，不能只改题库。
       ⚠ 这正是想要的：判分能力的边界应该看得见（见 ⑦ 的观测面）
```

### ⑦ 判分点能看见什么 —— eval 的 seam

```text
背景   实现时才发现这一格是空的：判分点判的到底是「什么东西」？
       `run` 吐的是事件流 + RunResult，里面有预算、重试次数、每个工具的结果。
       全给出去，判分点就能判任何东西 —— 而那正是问题

选择   投影成 `Transcript` = { outcome, answer, toolsUsed, turns } 四个字段
判据   和契约测试同一条：★seam 选在哪，覆盖到的就是哪一段★。
       四个字段是「一个用户能观察到的东西」的近似；
       预算和重试是★实现细节★，让判分点看见它们，题库就会长出
       「重试不超过 2 次」这种和「答得对不对」无关的题
代价   现在判不了成本和重试。
       ⏰ 反悔信号：阶段 8 做成本核算时，那一层要的是别的观测面 ——
       到时候是★另加一个投影★，不是把这个撑大
另外   `test/eval/transcript.test.ts` 里有一条断言写死了这四个字段名。
       IMPORTANT: 它是故意的 —— 想加第五个字段，先让那条断言红一次
```

### ⑧ 「退出码恒 0」的边界

```text
背景   ④ 写的是「永远 0，只报数字」。实现时撞上一个它没说的情况：
       ★题库文件本身写坏了★（少一个字段、判分点的 kind 拼错）

选择   ★题库不合法 → 非 0；分数低 → 0★
判据   ④ 的立论是「阈值 k 的输入 p0 未知，写任何 k 都是瞎选」——
       那条立论只覆盖★分数★。题库写坏是我们的文件坏了，
       和 p0 一点关系没有，是个确定性错误，本来就该红
代价   「恒 0」这个说法从此要带一句限定。
       ⚠ 不带的话下一个人会写出「无论如何 exit 0」的实现，
         然后题库坏掉时 eval 安静地报 0/0 —— ★而 0/0 和「全挂」长得一样★
```

### ⑨ 题库要不要校验，用什么校验

```text
背景   题库是 JSON，`JSON.parse` 的结果是 any/unknown ——
       少一个字段不会报错，只会变成 undefined 流进判分点

候选   a  不校验，信自己写的文件
       b  ★手写校验★，返回 Result
       c  上 zod（MyAgent 现在没有这个依赖）

判据   a 出局：⑧ 刚说过「0/0 和全挂长得一样」，静默的坏题库正是那个形态
       b vs c：加一个依赖要走 ADR 的四段。★现在只有一个形状要校验★，
       为 50 行付这个成本不划算；而 b 和项目已有的 createRunConfig /
       admitInput 是同一套写法（smart constructor + Result）

选择   b
代价   ToolName 加一格时有两处要改。★交给编译器盯着★ ——
       parse.ts 里有一个 ToolNamesMatch，手法同 ports.ts 的 KindsMatch
   ⏰ 反悔信号：★第二个★需要校验的外部格式出现时（阶段 4 的适配器响应），
      两份手写校验的重复就值一个依赖了
另外   ★id 重复直接拒★，不是「后面的覆盖前面的」——
       重复的 id 会让成绩单的失败明细指向两道题，事后没法定位。
       同 ADR 0012 §③ 拒绝同名录音带，同一条判据
```

## 后果

```text
✅ 用例格式在攒到三位数之前定死
✅ 判据档位有明确的升级前置条件，不会滑向「反正上 judge 最省事」
⛔ ★阶段 4 之前这一层没有信号★（④ 的代价，有意为之）
⛔ 不存模型完整输出 ⇒ 事后复盘受限（③ 的反悔信号）
```
