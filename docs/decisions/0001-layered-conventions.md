# 0001 · 更高层的架构规范：每层各用各的原生机制

日期：2026-09 　状态：生效

## 背景

领域层五个模块、28 条契约已经落地，验证装置（tsc / ESLint / 185 个测试 /
变异检查）在 **L1 函数层**是完整的。但更高的层没有任何机制：

- **L3 模块之间**：「领域层不许 import 端口层」这条规矩，现在只存在于人的脑子里。
- **L4 进程边界**：还没有 IO，但阶段 4 接模型时会有。
- **L6 业务语义**：★已经漂了★ —— `limit`(51 处) / `budget`(3 处) / 文档写「预算」，
  一个概念三个名字，而上述所有门禁**一个都发现不了**（是语义不是行为）。

行级契约标记（`// 契约⑥`）到这里就到头了：28 条里 16 条代码和测试都没提，
因为**它们落在类型里，不落在某一行**；而 L3 那条规矩是**一条不存在的边**，
根本没有行可以贴。

## 候选

```text
A  扩大标记体系：每层编 ID，代码/测试/ADR 互相引用（追溯矩阵）
B  ★每层各用各的原生机制★：依赖用 dependency-cruiser，边界用 schema，
   语义用词表，理由用 ADR —— 不追求统一 ID
C  上 C4 + Structurizr DSL，一套 DSL 描述全层级，图和文档都从它生成
D  什么都不加，靠 review
```

判据（可执行）：

```text
① 这一层的规矩被违反了，多久会被发现     当场 / 下次 review / 三个月后
② 维护成本随模块数怎么长                 线性 / 超线性
③ 已经踩过几次这个痛点                   0 次就不该加
```

## 决定

**选 B。**

```text
A  判据②不过 —— L1 就已经 16/28 追不上，往上必然崩
C  判据③不过 —— 5 个模块 0 个容器，纯成本；C4 的 Code 层官方都建议别画
D  判据①不过 —— limit/budget 这次就是 D 漏掉的，而且漏了不知道多久
```

各层的落地物：

| 层          | 机制                                                              | 落地时机          |
| ----------- | ----------------------------------------------------------------- | ----------------- |
| L3 依赖方向 | `dependency-cruiser`，规则：domain 不许 import adapters/ports     | 阶段 2            |
| L4 边界形状 | zod schema（同时是类型 / 校验 / 文档 / 夹具）；跨进程再谈契约测试 | 阶段 4 / 6        |
| L6 业务语义 | `docs/glossary.md` + 命名检查                                     | ★现在★（见 0002） |
| 理由本身    | 本目录的 ADR                                                      | 持续              |
