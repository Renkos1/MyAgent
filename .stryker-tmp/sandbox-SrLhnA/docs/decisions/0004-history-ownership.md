# 0004 · 对话历史归用例层，端口无状态

> 取代 0002 之前的口头约定（端口收增量）。ports.ts 契约⑤同时改写。

## 背景

阶段 2 定端口契约时选了「端口收这一轮的增量」。它推出一个不是自由选的结论：

```text
provider 的 HTTP API 无状态，每次要发全量
  → 收增量就意味着累加的活在适配器里
  → 端口有状态
  → 开一个 LlmSession 类型，把「有状态」写在名字上
```

当时写下的三条代价：每轮要 new 一个 session、「回退一轮重来」变难（历史在适配器肚子里）、
一个 session 不能并发用。

反悔信号写的是「需要编辑上一条消息重发或分支对话时」。**实际提前触发了** ——
阶段 2 还没结束就发现：历史看不见，意味着**测试断言不了「第 2 次请求带了什么」**。

## 候选

```text
① 端口收增量，适配器累加     原方案
                            代价：端口有状态；历史从外面不可见；不能并发
② 用例层拥有全部历史         端口无状态，每次收 { system, history }
                            代价：每次传全量；历史裁剪落到用例层
③ 用例层拥有，端口收增量      两边都要维护一份 —— ★两份会漂移★，直接排除
```

## 决定

**选 ②。** `LlmSession` 整个删除，`LlmPort` 变成两个无状态方法，
收 `LlmRequest = { system, history }`。

## 后果

```text
✅ 端口无状态 → 可并发、不需要生命周期管理、composition root 少一件事
✅ 「回退一轮重来」「编辑上一条重发」只是换一个数组
✅ ★历史变成可观察的★ —— FakeLlm.sent 现在是每次的全量，
   于是能断言「第 2 次请求带着第 1 轮的工具结果」

✅ 端口形状换了，★13 条用例层测试一条都没改★
   —— 因为它们断言的是行为不是调用形状。这是用 fake 而不是 mock 的回报。

⛔ 每次要序列化全量历史。阶段 8 之后长对话会变贵。
⛔ ★历史裁剪／压缩从此是用例层的职责★（阶段 8 的 context 管理落在这里）

⛔ TRAP: 改完立刻踩了一个别名 bug。history 原来写成可变数组 + push，
   而 `readonly TurnInput[]` ★只挡「通过这个引用改」，挡不住别名★ ——
   接收方存下的是引用，后面每 push 一次它手里那份"快照"就跟着变。
   实测症状：FakeLlm.sent[0] 里出现了第 2 轮才产生的工具结果。
   改成不可变累加（`history = [...history, item]`），和 LoopBudget 一致。
```

**反悔信号**：单次请求的历史稳定超过模型 context 的一半时，
用例层要开始做裁剪 —— 那时可能需要一个 `HistoryPolicy` 端口，
但历史的**所有权**仍然留在用例层。
